# MIRRO

Цифровой гардероб и примерка образов на AI-аватаре. Внутреннее имя проекта — `digital-wardrobe`.

Next.js (App Router) + TypeScript + Tailwind CSS + Supabase.

## Локальный запуск

```bash
npm install
cp .env.local.example .env.local   # и впишите ключи Supabase
npm run dev
```

Откройте http://localhost:3000.

## Переменные окружения

| Переменная | Где взять |
|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | Supabase → Project Settings → Data API (Project URL) |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | Supabase → Project Settings → API Keys (publishable / anon) |
| `RUNWARE_API_KEY` | Runware → Dashboard → API Keys. **Только сервер**, без `NEXT_PUBLIC_` |
| `RUNWARE_GARMENT_MODEL` | Необязательно. AIR модели для вырезания вещей, по умолчанию `google:4@3` (Nano Banana 2) |
| `RUNWARE_AVATAR_MODEL` | Необязательно. AIR модели для аватара, по умолчанию `google:4@3` (Nano Banana 2) |
| `RUNWARE_TRYON_MODEL` | Необязательно. AIR модели для примерки, по умолчанию `google:4@3` (Nano Banana 2) |

Ключи не хранятся в репозитории: локально — в `.env.local`, на Vercel — в
Project → Settings → Environment Variables (после изменения нужен Redeploy).
Без ключей Supabase приложение работает на тестовых данных. Без ключа Runware
вещи сохраняются с исходным фото.

## AI-вырезание вещи

При добавлении вещи пользователь выбирает её тип (Верх, Низ, …). Шаг «Обработка»
отправляет фото и тип на `/api/extract-garment` (серверный маршрут). Сервер с ключом
`RUNWARE_API_KEY` вызывает генеративную модель Runware (`imageInference`, фото в
`inputs.referenceImages`, задание в `positivePrompt`) и получает одну вещь на белом
фоне в стиле каталога. Ключ в браузер не попадает. Если Runware недоступен или
ключа нет, сохраняется исходное фото. Логи маршрута в Vercel начинаются с `RB:`.

## Аватар для «Примерки»

Если у пользователя нет аватара, «Примерка» предлагает его создать: селфи (обязательно),
фото в полный рост и рост/вес (необязательно). Сервер (`/api/create-avatar`, логи `AV:`)
отправляет фото в Nano Banana (`imageInference`) и возвращает аватар в полный рост.
Браузер сохраняет его в бакет `avatars` (`<user>/avatar-<время>.jpg`), путь — в
`profiles.avatar_path`; старый файл удаляется. Исходные фото не сохраняются.

## Примерка

Панель «Примерки» показывает вещи из таблицы `items`. Пользователь выбирает по одной
вещи в категории и нажимает «Примерить». Браузер отправляет только id вещей на
`/api/try-on` (логи `TO:`); сервер сам берёт аватар и фото вещей из хранилища, просит
Nano Banana одеть аватар и сохраняет результат в закрытый бакет `tryons`
(`<user>/<ключ>.jpg`) и таблицу `try_on_results`. Ключ — хэш пути аватара и id вещей,
поэтому тот же набор на том же аватаре показывается из кэша без новой генерации, а
после смены аватара примерка делается заново. Миграция —
`supabase/migrations/20261005120000_try_on_results.sql`.

## Образы

«Сохранить образ» в Примерке записывает строку в `looks` (название, папка, `image_url` —
путь готовой примерки в бакете `tryons`, без новой генерации) и вещи образа в `look_items`.
Экран «Образы» и страница образа читают эти таблицы и `folders` из браузера (RLS — только
свои строки): избранное, переименование, комментарий, перенос в папку и удаление
сохраняются в базе. «Изменить образ» открывает Примерку с вещами образа
(`/try-on?items=…`). Новых таблиц и SQL не нужно — всё есть в начальной схеме.

## Профиль

Фото профиля (отдельно от аватара) сжимается в браузере и хранится в закрытом бакете
`profile-photos` (`<user>/photo-<время>.jpg`), путь — в `profiles.photo_path`.
«Удалить аккаунт» в «Приватность и данные» сначала удаляет все файлы пользователя из
бакетов `items`, `avatars`, `tryons`, `profile-photos` через Storage API, затем функция
`delete_my_account()` в базе проверяет, что файлов не осталось, и удаляет все строки и сам
аккаунт. Миграция — `supabase/migrations/20261006120000_profile_photos_and_account_deletion.sql`.

## Токены бета-доступа

У каждого пользователя один баланс (`profiles.tokens_balance`, «из скольких» —
`tokens_total`). Стартовое значение задано в одном месте — SQL-функция
`beta_start_tokens()` (сейчас 10, см. миграцию `20261009120000_beta_start_tokens_10.sql`). Новая генерация (вырезание вещи, новая примерка,
аватар) стоит 1 токен: сервер проверяет баланс до вызова Runware (при нуле — HTTP 402
`no_tokens`) и списывает функцией `spend_token()` только после успеха. Повтор
сохранённой примерки и неудачи бесплатны. Из браузера баланс изменить нельзя (триггер
`protect_profile_tokens`). Логи списаний начинаются с `TK:`. Миграция и SQL для
пополнения — `supabase/migrations/20261007120000_beta_tokens.sql`.

## Оплата подписки (ЮKassa, этап 1 — тест)

«Оформить» на экране «Подписка» вызывает `/api/payments/create`: сервер создаёт платёж в
ЮKassa (сумма — с сервера, `capture: true`, `save_payment_method: true`, Idempotence-Key,
metadata с id пользователя, тарифом и номером заказа) и отдаёт ссылку на страницу оплаты.
После оплаты ЮKassa возвращает на `/profile/subscription/result?order=…`, где
`/api/payments/status` проверяет платёж через `GET /v3/payments/{id}` и при успехе записывает
подписку и сохранённую карту в `subscriptions` (сервисным ключом; браузер эти таблицы только
читает). Принимаются только тестовые ключи (`test_…`). Логи — `YK:`.
Переменные: `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, `SUPABASE_SERVICE_ROLE_KEY`,
необязательно `APP_URL`. Миграция — `supabase/migrations/20261010120000_payments_subscriptions.sql`.

**Webhook ЮKassa** — `POST /api/payments/webhook` (события `payment.succeeded`,
`payment.canceled`, `payment.waiting_for_capture`). Включает подписку, даже если пользователь
не вернулся в приложение. Телу уведомления не доверяет: берёт id платежа и заново запрашивает
платёж в API ЮKassa. Возврат в приложение и webhook используют общую идемпотентную логику
(`lib/payments.server.ts`): подписка включается один раз. Логи — `YK[webhook]:` / `YK[return]:`.

**Автопродление** — `GET /api/cron/renew`, Vercel Cron раз в сутки в 06:00 UTC (09:00 МСК),
расписание в `vercel.json`. Списывает плату с сохранённой карты у подписок, у которых закончился
период; отменённые не трогает. Не прошло — статус `past_due`, доступ сохраняется ещё 3 дня,
повтор раз в сутки; потом `expired`. От двойного списания защищают уникальный индекс в базе,
Idempotence-Key и идемпотентное применение платежа. Доступ — только с заголовком
`Authorization: Bearer $CRON_SECRET` (Vercel добавляет его сам). Логи — `YK[cron]:`.
Миграция — `supabase/migrations/20261011120000_subscription_renewal.sql`.

**Чеки 54-ФЗ** («Чеки от ЮKassa») — каждый платёж (первая оплата, автосписание, в будущем —
пакет токенов) создаётся с `receipt`: почта пользователя, одна позиция, `tax_system_code: 2`
(УСН «доходы»), `vat_code: 1` (без НДС), `payment_subject: service`, `payment_mode: full_payment`.
Сборка чека — `buildReceipt` в `lib/yookassa.ts`; без чека платёж создать нельзя (обязательный параметр).

**Токены по тарифу** (модель «сброс») — новый пользователь получает 10 токенов один раз,
они не пополняются. Каждая успешная оплата Premium / Premium+ (первая и каждое продление)
ставит баланс 50 / 150, остаток не переносится. Отмена и окончание подписки баланс не трогают.
Начисляет только сервер через `grant_plan_tokens` (один платёж — одно начисление, таблица
`token_grants`). Миграция — `supabase/migrations/20261012120000_plan_tokens.sql`. Логи — `TOKENS[...]:`.

**Отмена** — `POST /api/subscription` (`{"action":"cancel"|"resume"}`): отключает/включает
автопродление, доступ сохраняется до конца оплаченного периода.
